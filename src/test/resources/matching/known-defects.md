# Known Defects — LimitOrderExecutionService matching-pure-logic refactor

Categories:
- ① not-a-problem — behavior is intentional / benign, no action needed.
- ② unadjudicated, needs investigation — observed during characterization, not yet decided whether/how to fix.
- ③ fixed now — resolved in this refactor cycle.

| # | Category | Description |
|---|----------|-------------|
| 1 | ② | `OrderBookEntry.willBeFilledCompletely()` is dead code: 0 call sites in `src/`. It is never invoked by `LimitOrderExecutionService` or any other production class. Kept as-is pending a decision on whether to delete it or wire it in. |
| 2 | ② | The sorting axis for order-book priority is distributed across three independent components that must stay in agreement: (a) the in-memory `Comparator` built in `LimitOrderMatchPlanner`'s private `sortByPriority` method (price then `createdAtEpochMillis`, direction flipped by taker method), (b) `RedisOrderBookRepository.fetchMatchingEntries`'s Redis ZSET direction/truncation semantics, and (c) `Order`'s market-order sentinel prices (`MARKET_BUY_SENTINEL_PRICE = 999999999`, `MARKET_SELL_SENTINEL_PRICE = 0.01`). No single source of truth enforces that all three agree; a change to one without the others could silently break matching priority. Needs investigation into consolidating the sort/priority contract. |
| 3 | ② | The early return in `LimitOrderExecutionService.distributeEvent` (`if (plan.allocations().isEmpty()) { return List.of(); }`, immediately after the `matchPlanner.plan(...)` call) fires whenever every candidate entry in the matcher's sorted list is exhausted (`OrderBookEntry.isExhausted()`), since `FillPlan.allocations()` will be empty in that case. In that case the method returns before reaching the exhausted-entry deletion loop (the `for (OrderBookEntry entry : plan.exhaustedEntries())` loop, near the end of the method inside the Redis-update `try` block), so those entries are never removed from Redis. They persist indefinitely and continue to consume space in the `fetchSize=100` fetch window on every subsequent call for that price/side, until removed by some unrelated path. Marked do-not-fix this cycle: fixing this early-return short-circuit is itself a behavior change and is out of scope for this refactor (test/extraction-only, no behavior changes permitted). Characterized as-is in `LimitOrderExecutionExhaustedEntryCharacterizationTest` (case 3) and in `LimitOrderMatchPlannerTest`'s empty-candidate-list and all-exhausted coverage. |
