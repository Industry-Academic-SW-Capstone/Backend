# create-issue

대화·코드 맥락에서 이슈 내용을 추론해 GitHub 이슈를 만들고, 최신 `develop`에서
`<접두사>/#<번호>` 형식의 작업 브랜치를 분기한다. 팀 컨벤션(이슈 템플릿, 브랜치
네이밍)에 맞춰 동작한다.

응답과 질문은 모두 **한국어**로 한다.

## 0. 전제조건 확인 (실패 시 중단하고 안내)

먼저 아래를 확인한다. 하나라도 실패하면 진행하지 말고 사용자에게 알린다.

```bash
gh auth status          # gh 설치·인증 확인 (미설치면 `brew install gh`, 미인증이면 `gh auth login` 안내)
git rev-parse --show-toplevel   # git 저장소인지 확인
git remote -v           # 원격 확인 — 대상 저장소 파악
```

- 원격이 여러 개여서 대상 저장소가 모호하면 어느 저장소에 이슈를 만들지 사용자에게 확인한다.
- `gh` 미인증이면 `gh auth login`은 대화형이므로 사용자에게 `! gh auth login` 실행을 안내하고 중단한다.

## 1. 맥락 수집 (추론 위주)

지금까지의 대화, 최근 diff, 관련 코드에서 다음을 **최대한 추론**한다. 추론이
어려운 항목만 사용자에게 간단히 묻는다.

- **제목** — 간결한 한 줄. 이슈 유형 이모지를 접두로 붙인다 (아래 매핑 참고).
- **유형** — 아래 5종 중 맥락에 가장 맞는 것을 고른다.
- **Summary** — 이 이슈가 무엇을/왜 하는지 2~3문장.
- **To Do** — 실제 작업 단위를 체크리스트 항목으로 (`- [ ]`).

한꺼번에 다 묻지 말고, 부족한 것만 자연스럽게 물어본다.

## 2. 유형 → 이모지 / 브랜치 접두사 / 라벨 매핑

| 유형 | 제목 이모지 | 브랜치 접두사 | 저장소 라벨 |
|------|:-----------:|:-------------:|-------------|
| 기능 구현   | 🚀 | `feat`     | `🚀 Feat`      |
| 버그 해결   | 🔨 | `fix`      | `🏷 Fix`       |
| 리팩토링    | 🧹 | `refactor` | `🖌️Refactor`   |
| 환경설정    | 🧭 | `chore`    | `🧭 Chore`     |
| 문서화     | 📑 | `docs`     | `📑 Docs`      |

추론한 유형을 **제안하고 맞는지 확인**받는다 (예: "환경설정(🧭 → chore)으로 볼게요, 맞나요?").

## 3. 라벨 선택

위 매핑 표의 유형별 라벨을 기본으로 사용한다. 다만 라벨명은 저장소에서 바뀔 수
있으므로, 생성 직전 실제 라벨 목록을 조회해 **정확한 이름**을 확인한다.

```bash
gh label list --repo <owner/repo> -L 100
```

- 매핑 표의 라벨이 목록에 있으면 그 이름 그대로 사용하고, 맥락상 추가로 맞는
  라벨이 있으면 함께 붙인다. **없는 라벨을 새로 만들지 않는다.**
- 담당자는 항상 본인으로: `--assignee @me`.

## 4. 미리보기 & 승인 (필수 게이트)

이슈를 만들기 전에 아래를 사용자에게 보여주고 **명시적 승인**을 받는다.
외부에 공유되는 저장소이므로 이 단계를 건너뛰지 않는다.

- 대상 저장소
- 제목
- 본문 (아래 포맷)
- 라벨 / assignee
- 분기될 브랜치명 (`<접두사>/#<번호>` — 번호는 생성 후 확정)

### 이슈 본문 포맷 (저장소 템플릿 준수)

```
### 🚀 Summary

<한두 문단 요약>

### 📝 To Do

- [ ] <작업 항목>
- [ ] <작업 항목>
```

## 5. 이슈 생성

본문은 셸 이스케이프 문제를 피하기 위해 **파일로 저장한 뒤 `--body-file`** 로 넘긴다.
(스크래치패드 디렉토리에 임시 파일을 쓴다.)

```bash
gh issue create \
  --repo <owner/repo> \
  --title "<이모지 제목>" \
  --body-file <임시 본문 파일 경로> \
  --assignee @me \
  --label "<라벨1>" --label "<라벨2>"   # 라벨 없으면 이 옵션 생략
```

생성 결과로 나온 이슈 URL에서 **이슈 번호**를 파싱한다 (URL 끝의 숫자).

## 6. develop에서 브랜치 분기

브랜치 베이스는 **항상 `develop`** 이다.

먼저 안전 점검:

```bash
git status --porcelain   # 출력이 있으면(= 커밋 안 된 변경) 중단하고 사용자에게 알림
```

- 커밋되지 않은 변경이 있으면 브랜치를 전환하지 말고, commit/stash 후 다시 시도하도록 안내한다.

이상 없으면 분기:

```bash
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c <접두사>/#<이슈번호>      # 예: chore/#189
```

- 같은 이름의 브랜치가 이미 있으면 새로 만들지 말고 사용자에게 알린다.

## 7. 결과 보고

다음을 한국어로 간단히 보고한다.

- 생성된 이슈: 제목 + URL (+ 번호)
- 분기된 브랜치명 + 베이스(`develop`)
- 다음 작업을 이 브랜치에서 이어가면 된다는 안내

## 참고

- 브랜치명에는 **슬러그를 붙이지 않는다** (`chore/#189` O, `chore/#189-add-skill` X). 저장소 관례.
- 커밋·PR 생성은 이 스킬의 범위가 아니다. 사용자가 별도로 요청할 때 진행한다.
